# 기록 페이지 서버 페이지네이션·검색 설계

## 목표

기록 페이지의 평가·교정 탭이 전체 기록을 한 번에 내려받지 않고, 검색 조건에 맞는 기록을 페이지당 10개씩 서버에서 조회하도록 한다.

## 확정된 사용자 동작

- 평가 탭은 문항 텍스트를 검색한다.
- 교정 탭은 교정 입력 문장을 검색한다.
- 검색은 입력 즉시 적용하고 대소문자를 구분하지 않는다.
- 검색어를 바꾸거나 탭을 바꾸면 해당 목록의 첫 페이지로 돌아간다.
- 정렬은 기존과 같이 최신 기록(`id DESC`) 우선이다.
- 페이지당 항목 수는 10개다.
- 검색 결과가 없으면 검색 결과 전용 빈 상태를 보여 준다.
- 이전·다음 페이지 버튼은 이동할 수 없을 때 비활성화한다.

## API 계약

평가와 교정 목록 API는 같은 페이지 응답 형식을 사용한다.

```ts
type PaginatedResponse<T> = {
  items: T[];
  total: number;
  limit: 10;
  offset: number;
};
```

요청 형식:

```text
GET /api/attempts?limit=10&offset=0&search=park
GET /api/corrections?limit=10&offset=0&search=park
```

- `limit`은 생략하면 10이며, 서버는 최대 10으로 제한한다.
- `offset`은 생략하면 0이며 음수는 0으로 보정한다.
- `search`는 trim한 뒤 빈 값이면 검색 조건을 적용하지 않는다.
- 검색어는 SQL 파라미터로 전달하고, `%`와 `_`를 이스케이프해 부분 문자열 검색의 입력값으로만 취급한다.
- `total`은 검색 조건을 적용한 전체 개수다.
- `items`는 검색·정렬·offset·limit을 모두 적용한 결과다.

평가 목록은 `questions.text`에 대해 검색하고, 교정 목록은 `corrections.input_text`에 대해 검색한다. 목록 조회는 매 요청마다 `COUNT(*)`와 페이지 조회를 실행하며, 기존 상세 조회·재시도·오디오 API는 변경하지 않는다.

## 구현 구조

- `server/src/repo/attempts.js`: 검색 가능한 평가 count/list 쿼리를 추가하고 문항 조인을 유지한다.
- `server/src/repo/corrections.js`: 검색 가능한 교정 count/list 쿼리를 추가한다.
- `server/src/routes/attempts.js`, `server/src/routes/corrections.js`: query string을 정규화해 repository에 전달하고 페이지 응답을 반환한다.
- `web/src/types.ts`: 공통 페이지 응답 타입을 추가한다.
- `web/src/pages/HistoryPage.tsx`: 현재 탭·검색어·offset을 상태로 보유하고 목록 요청에 query string을 붙인다. 서버 응답의 `items`만 렌더링하며, 검색·탭 전환 때 offset을 0으로 리셋한다.
- `web/src/styles/globals.css`: 기록 검색 입력과 페이지 이동 영역을 기존 행 목록 문법에 맞춰 배치한다.

폴링은 현재 탭에서만 활성화하며, 검색어와 offset이 바뀌면 새 요청 조건으로 즉시 다시 시작한다. 폴링 응답의 조건이 바뀐 뒤 이전 응답이 화면에 남지 않도록 요청 조건이 바뀔 때 현재 데이터를 비운다.

## 오류·경계 조건

- 목록 API 오류는 기존 탭별 오류 문구를 유지한다.
- `offset`이 현재 결과 범위를 벗어나면 빈 `items`를 반환하며, 화면은 offset을 마지막 유효 페이지로 자동 보정하지 않는다. 새 기록이 생겨 페이지 범위가 바뀌어도 현재 페이지 의도를 보존한다.
- 검색 결과가 0개일 때 기존 “기록이 아직 없음” 메시지 대신 검색어를 지우도록 안내한다.
- 상세 행을 열어 둔 상태에서 검색·페이지·탭이 바뀌면 열린 행과 재시도 상태를 초기화한다.
- 재시도 후에는 현재 페이지 조건으로 목록을 다시 조회한다.

## 테스트 전략

### 서버 계약

- 평가 목록이 `limit=10`, `offset`을 적용하고 `total`을 전체 검색 결과 개수로 반환하는지 검증한다.
- 평가 검색이 문항 텍스트에 대해 대소문자 구분 없이 동작하는지 검증한다.
- 교정 목록이 같은 페이지 계약을 따르고 입력 문장 검색만 적용하는지 검증한다.
- 기본값·음수 offset·10 초과 limit이 안전하게 정규화되는지 검증한다.
- 기존 상세 조회와 재시도 계약은 대표 기존 테스트로 유지한다.

### 웹 핵심 전이

- 첫 요청이 페이지 크기 10과 offset 0으로 호출되는지 검증한다.
- 다음 페이지가 offset 10으로 호출되고, 이전 페이지가 offset 0으로 돌아오는지 검증한다.
- 검색 입력이 현재 탭 API의 `search` query를 갱신하고 offset을 0으로 리셋하는지 검증한다.
- 탭 전환 시 검색어와 페이지가 초기화되고 새 탭 API를 호출하는지 검증한다.
- 페이지 이동 버튼의 접근 가능한 이름과 disabled 상태를 검증한다.

단순 CSS 세부 조합과 모든 문구 변형은 테스트하지 않는다. 실제 서버 목록 endpoint와 HistoryPage의 요청·상태 전이를 우선한다.
